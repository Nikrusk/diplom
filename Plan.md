# План тестирования приложения fmh_android_updated

## Определение объекта тестирования

Объектом тестирования является приложение `fmh_android_updated` в виде исходного кода нескомпилированного приложения «Мобильный хоспис» для Android текущей конфигурации по состоянию на 26.09.2026 г.

---

## Цели тестирования

Целями тестирования являются:

- определение входных требований к приложению;
- определение реализованного функционала приложения на текущем этапе разработки;
- тестирование реализованного функционала приложения на текущем этапе разработки;
- тестирование пользовательского интерфейса приложения на текущем этапе разработки;
- определение возможного объёма автоматизации тестирования приложения по результатам проведённого тестирования.

---

## Границы приложения

Приложение будет тестироваться по следующему функционалу:

- билд приложения;
- установочное тестирование приложения на заданном заказчиком эмуляторе без проведения кроссплатформенного тестирования;
- запуск приложения;
- страница авторизации пользователя по предоставленной заказчиком паре логин‑пароль;
- главная страница приложения;
- навигация между страницами приложения;
- страница «Новости»;
- возможность публикации новой новости;
- возможность редактировать имеющуюся новость;
- возможность удалять новости;
- валидация полей создания и редактирования новости по предполагаемым или указанным критериям;
- страница «О приложении»;
- страница «Цитаты».

Приложение подвергается следующим типам тестирования:

### Для отдельных полей

- позитивное тестирование (корректные данные, корректные шаги);
- негативное тестирование (введение невалидных данных, некорректные шаги).

### Для всей системы

- функциональное тестирование;
- юзабилити‑тестирование;
- тестирование пользовательского интерфейса.

## Условия тестирования

### Общие условия

- ОС: Windows 11;
- файл проекта: `fmh_android_updated.zip`;
- архиватор: WinRAR;
- среда разработки: Android Studio;
- Android Gradle Plugin;
- система сборки: Gradle;
- Compile SDK;
- Build Tools;
- инструменты автоматизации: Espresso, Allure, JUnit.

Тестирование будет проводиться по чек‑листу и составленным тест‑кейсам. Чек‑лист включает в себя короткие условия проверок; тест‑кейс служит для проверки корректности работы полей и отдельных элементов приложения.

Тестирование модуля календаря и часов на страницах «Создание новости» и «Редактирование новости» не входит в задачи данного тест‑плана. Проверка данных модулей будет проведена формально по минимальному набору критериев по тест‑кейсу.

### Тестирование пользовательского интерфейса

- конфигурация оборудования: указанная в общих условиях;
- эмулятор: Pixel 9, Android API 36;
- проект приложения: исходный код для Android Studio.

## Техники тест‑дизайна с обоснованием

Для покрытия функционала приложения применяются следующие техники тест‑дизайна:

1. **Классы эквивалентности и граничные значения**  
   Применяется для проверки полей ввода на страницах авторизации, создания и редактирования новости.  
   *Обоснование:* у полей ввода (заголовок, категория, описание новости) есть ограничения по длине и типу символов. Разбиение на классы (валидные данные, пустое поле, спецсимволы, превышение длины, значения на границах допустимой длины) даёт максимальное покрытие при минимальном числе проверок.

2. **Тестирование по таблицам принятия решений (decision table)**  
   Применяется для проверки комбинаций заполненности полей при создании и редактировании новости (все поля заполнены / пустой заголовок / пустая категория / пустое описание и т. д.).  
   *Обоснование:* поведение системы зависит от сочетания состояний нескольких полей, а не каждого по отдельности. Таблица решений позволяет компактно зафиксировать все комбинации без избыточных кейсов.

3. **Тестирование переходов состояний (state transition)**  
   Применяется для жизненного цикла новости (черновик → опубликована → отредактирована → удалена) и для состояний приложения (закрыто → запущено → авторизован → основная страница → раздел новостей).  
   *Обоснование:* функционал приложения построен на переходах между экранами и статусами. Ошибки чаще всего возникают при нетипичных последовательностях действий (например, удаление отредактированной новости, повторная авторизация после выхода).

4. **Исследовательское (ad‑hoc) тестирование**  
   Дополняет формальные проверки на этапе юзабилити‑ и UI‑тестирования.  
   *Обоснование:* чек‑лист не гарантирует обнаружения дефектов вёрстки и нестандартного поведения интерфейса (некликабельные элементы, обрезанный текст, нестандартные жесты), которые сложно предвидеть в тест‑кейсах заранее.

5. **Смоук‑тестирование**  
   Минимальный набор проверок (билд, установка, запуск, авторизация, переход на основные страницы) выполняется после каждой пересборки приложения.  
   *Обоснование:* позволяет быстро убедиться в работоспособности билда и не тратить время на детальное тестирование заведомо нерабочей сборки.

## Сортировка тест‑кейсов по степени автоматизации

По результатам анализа объёма работ тест‑кейсы делятся на две группы. Полное покрытие всего функционала автотестами не предусмотрено: автоматизация выполняется в учебных целях — для демонстрации навыков написания автотестов и выявления дефектов.

### Планируется автоматизировать

(стабильный, часто повторяемый функционал с предсказуемым результатом)

- проверка сборки и запуска приложения (smoke);
- авторизация с валидной парой логин‑пароль;
- авторизация с невалидными данными (пустые поля, неверный пароль);
- навигация между страницами приложения (переход в разделы «Новости», «О приложении», «Цитаты» и обратно);
- публикация новой новости со всеми заполненными полями;
- редактирование существующей новости с сохранением;
- удаление новости с подтверждением;
- валидация полей создания и редактирования новости: пустые поля, превышение допустимой длины, ввод спецсимволов;
- проверка отмены действий (закрытие формы создания/редактирования новости без сохранения);
- проверка содержимого страниц «О приложении» и «Цитаты».

*Обоснование:* эти проверки выполняются при каждой пересборке приложения, имеют однозначный ожидаемый результат и хорошо поддаются UI‑автоматизации на Espresso с отчётами в Allure.

*Особенность негативных проверок:* негативные тест‑кейсы (невалидные данные, некорректные сценарии) могут завершаться падением — это ожидаемый результат их выполнения. В отчёте Allure для таких тестов указывается, что падение является ожидаемым поведением и фиксирует найденный дефект либо корректную обработку невалидных данных приложением.

### Проверяется вручную

- юзабилити‑тестирование (удобство навигации, читаемость, логичность расположения элементов);
- визуальная проверка пользовательского интерфейса (вёрстка, адаптация под разрешение экрана, обрезание текста, корректность изображений и цветов);
- исследовательское тестирование после внесения правок;
- формальная проверка модуля календаря и часов по минимальному набору критериев (включена в чек‑лист как ручная проверка);
- проверка страницы «Главная» (статический контент — экономически нецелесообразно покрывать автотестами).

*Обоснование:* данные проверки требуют визуальной оценки и субъективных суждений. Автоматизация таких кейсов затратна по времени и не окупается на этапе текущей разработки.

*Подход к разработке автотестов:* на начальном этапе автотесты создаются с помощью инструмента Espresso Test Recorder, после чего проводится их рефакторинг — вынос взаимодействий с элементами интерфейса в Page Object Model (с возможным использованием класса Steps). В тестах не используются явные ожидания вида `sleep()` и жёсткие задержки. Тесты разбиты на отдельные классы по функциональному признаку (авторизация, новости, «О приложении», «Цитаты») и не зависят от порядка запуска друг от друга. При использовании Allure применяются дополнительные аннотации отчёта (`@Epic`, `@Feature`, `@Story`, `@Severity`, `@Step`, `@Description`) и логирование шагов.

## Перечень необходимых специалистов для автоматизации

Для выполнения работ по автоматизации тестирования необходимы следующие специалисты:

1. **QA‑инженер (ручное тестирование)**  
   Обязанности: составление чек‑листа и тест‑кейсов, ручное прохождение проверок, регистрация и подтверждение дефектов.

2. **QA‑инженер по автоматизации (AQA)**  
   Обязанности: настройка тестового окружения (Android Studio, Gradle, эмулятор), написание UI‑автотестов на Espresso/JUnit, настройка генерации отчётов Allure, интеграция тестов в процесс сборки.

3. **Разработчик мобильного приложения (консультационное участие, по необходимости)**  
   Обязанности: предоставление доступа к тестовым стендам, помощь при разборе локализованных дефектов, уточнение ожидаемого поведения функционала, не покрытого требованиями.

Минимальная конфигурация команды: один QA‑инженер, совмещающий ручное тестирование и автоматизацию, при участии разработчика заказчика по необходимости. При увеличении объёма автотестов рекомендуется выделение отдельного специалиста по автоматизации.

## Интервальная оценка с учётом рисков

Оценка трудозатрат выполняется интервальным методом (пессимистичный / реалистичный / оптимистичный сценарий) с учётом влияния выявленных рисков.

| Этап работ | Оптимистичный | Реалистичный | Пессимистичный |
| --- | --- | --- | --- |
| Составление плана тестирования, создание чек‑листа, создание тест‑кейсов | 45 ч | 60 ч | 75 ч |
| Настройка окружения, написание и отладка автотестов | 80 ч | 100 ч | 140 ч |
| Подготовка отчётных документов по итогам тестирования | 20 ч | 30 ч | 40 ч |
| **Итого** | **145 ч** | **190 ч** | **255 ч** |

### Влияние рисков на оценку

- **Невозможность проведения тестирования по определённым условиям** (недоступность исходников, неработоспособность билда) — в пессимистичном сценарии добавляется до 20 ч на согласования и выяснение условий с заказчиком.
- **Увеличение сроков этапов из‑за дополнительных действий, не предусмотренных документом** (например, донастройка окружения, обновление версий SDK и инструментов) — учтено в реалистичном сценарии.
- **Значительное число обнаруженных дефектов** (расходы на подтверждение, регистрацию и перепроверку дефектов) — является основным фактором пессимистичной оценки по этапу написания автотестов: итеративное обновление тест‑кейсов и автотестов после исправления дефектов.

За базовую плановую оценку принимается реалистичный сценарий — **190 ч**. Пессимистичный сценарий (**255 ч**) используется для планирования буфера проекта.

## Тестовая документация на проекте

По итогам работ заказчику передаётся следующий комплект документации:

### Ручное тестирование

1. План тестирования (настоящий документ).
2. Чек‑лист проверок с отметками о прохождении.
3. Тест‑кейсы (позитивные и негативные) по проверяемому функционалу с результатами выполнения.
4. Отчёт о результатах ручного тестирования: статистика пройденных/проваленных проверок, описание дефектов с приоритетами и шагами воспроизведения (баг‑репорты).

### Автоматизация

5. Описание тестового окружения: инструкции по настройке Android Studio, Gradle, эмулятора Android API 36 и запуску тестов.
6. Исходный код автотестов (Espresso, JUnit) с комментариями и структурой проекта: Page Object Model, разделение тестов по классам в соответствии с функционалом приложения.
7. Отчёты о прогоне автотестов в Allure (Allure‑отчёт): результаты каждого прогона, шаги, вложения (скриншоты, логи) по падениям.

### Итоговые документы

8. Сводный отчёт по итогам тестирования (`Result.md`): объединённые результаты ручного и автоматизированного тестирования, сравнение подходов, найденные проблемы, затраченное время, итоговая статистика дефектов, рекомендации по устранению и повторному тестированию.
9. Файл `README.md` с описанием процедуры запуска автотестов.
10. Архив `allure-results.zip` с отчётом о результатах прогона тестов.
11. Баг‑репорты: оформленные issues в GitHub либо Excel‑таблица с баг‑репортами, размещённая в репозитории.
12. Оценка потенциального объёма дальнейшей автоматизации: список оставшегося функционала, целесообразного для покрытия автотестами на следующих этапах разработки.
