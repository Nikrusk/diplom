# Result.md — Итоговый отчёт по дипломному проекту

**Проект:** Автоматизация тестирования мобильного приложения «МП ФМХ» (fmh_android)
**Инструменты:** Java, Android Studio, Espresso, UI Automator, Allure, Gradle
**Окружение:** эмулятор Android (API 33), Windows 10/11

---

## 1. Сравнение ручного и автоматизированного тестирования

| Критерий | Ручное тестирование | Автоматизированное тестирование |
|---|---|---|
| Первый прогон полного набора | ~3–4 ч (26 проверок вручную с логином и переходами) | 17 мин 36 с |
| Повторный (регрессионный) прогон | те же ~3–4 ч, качество исполнения зависит от тестировщика | те же 17–18 мин, воспроизводимость 100% |
| Воспроизводимость результата | возможны пропуски шагов, усталость | каждый прогон идёт по одному и тому же сценарию |
| Доказательная база | скриншоты, снятые вручную | автоматически прикладываемые скриншоты Allure и стектрейсы |
| Проверка мелких деталей UI | сильная сторона — человек замечает аномалии | проверяет только заявленные проверки |
| Стоимость повторных прогонов | растёт линейно с количеством регрессий | практически не растёт |
| Обнаружение новых дефектов | эффективнее на новых областях (exploratory) | эффективнее как защита от регрессий |

**Вывод.** Ручное тестирование быстрее осваивает новую функциональность и гибче в исследовании, но при каждом регрессионном прогоне требует полной затраты времени. Автоматизация окупилась уже в этом проекте: 26 проверок выполняются за 17,5 минут без участия человека, а Allure-отчёт с автоскриншотами сразу даёт доказательную базу. Оптимальная стратегия — ручное exploratory-тестирование новой функциональности + автотесты на стабилизированные сценарии.

## 3. Найденные проблемы

### 3.1 Дефекты приложения

Дефектов, блокирующих функциональность, не обнаружено. Все 26 автотестов пройдены успешно: авторизация (валидные и невалидные данные), навигация по меню и табам, полный цикл работы с новостями, цитаты, сидовые данные — во всех случаях фактический результат совпал с ожидаемым.

### 3.2 Проблемы инфраструктуры автоматизации и их решения

| Проблема | Проявление | Решение |
|---|---|---|
| Скриншот при падении снимался после закрытия приложения | В Allure-отчёте вместо экрана приложения оказывался лаунчер или лок-скрин | Добавлен ручной снимок `allureScreenshot` внутри `catch` до проброса исключения; `ScreenshotRule` оставлен как страховка |
| На скриншотах лок-скрин вместо приложения | Экран эмулятора засыпал во время долгого прогона | Перед прогоном: `adb shell svc power stayon true` |
| Смешивание результатов разных прогонов | В отчёт попадали результаты старых запусков | Очистка `files/allure-results` перед каждым прогоном |
| Падение теста после правок кода | Студия гоняла устаревший код теста | Пересборка через «Clean and Assemble Project with Tests» перед прогоном |
| Результаты не выгружались с устройства | Отчёт пустой после прогона | Выгрузка через `adb exec-out run-as ... tar -c files/allure-results` |

## 5. Выводы

1. Автотесты покрывают ключевые пользовательские сценарии приложения: авторизацию, навигацию, полный CRUD-цикл новостей с фильтрацией и сортировкой, просмотр цитат.
2. Время полного регрессионного прогона сокращено с ~3–4 часов (ручной прогон) до ~18 минут.
3. Настроена доказательная база: Allure-отчёт автоматически фиксирует шаги, стектрейсы и скриншоты экрана в момент падения.
4. Для дальнейшего развития проекта рекомендуются: прогон на реальных устройствах, подключение CI (GitLab CI / GitHub Actions) для запуска suite по коммиту и расширение покрытия на остальные разделы приложения.
